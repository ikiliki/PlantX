🟢 Auth issue fixed (PR #61)

Google Identity token ↓ POST /api/session/google ↓ verifyGoogleIdToken() ├─ RS256 signature against Google JWKS (keys cached by max-age) ├─ keys unreachable / unknown key → 401, never trust claims └─ then aud · iss · exp · email_verified ↓ admin only if email = PLANTX_BOOTSTRAP_ADMIN_EMAIL (env)
Now: a forged token with the right claims but no Google signature gets 401 and no session. An e2e test (e2e/auth.spec.ts, @prod) checks this on every PR and after every production deploy.

🔐 Authentication request flow

Browser ↓ LoginPage / AuthDialog ↓ Google Identity Services ↓ ID token POST /api/session/google ↓ verifyGoogleIdToken() (Google JWKS signature check) ↓ sessionService.loginWithGoogle() ↓ existing member / pending signup / bootstrap admin ↓ setSession() ↓ signed HttpOnly cookie: plantx_session ↓ future API requests use credentials: include ↓ getSignedCookie() ↓ active user lookup ├─ requireUser() └─ requireAdmin()

Credential handling

  • No bearer JWT stored in localStorage.
  • Session cookie is signed with SESSION_SECRET.
  • HttpOnly.
  • Secure in production.
  • SameSite=Lax.
  • Disabled users lose access on the next request.

PP / test login isolation

PREVIEW / PP PLANTX_PREPROD = 1 PLANTX_TEST_TOKEN = set VERCEL_ENV != production ↓ test login enabled PRODUCTION VERCEL_ENV = production ↓ preprodEnabled() = false ↓ test login disabled

A bilingual living-plant platform centered on a digital greenhouse. Plants have identity/passport data, photos, class metadata, care actions, history and eventually trust, lineage and market state.

Current technical stack

MVP user model we discussed

Guest ├─ browse / wiki ├─ up to 3 plants on this device └─ no AI scans Free member ├─ persistent greenhouse ├─ care / tasks / passport └─ 3 AI scans/day, reset 00:00 Israel (live) Premium ├─ everything in Free └─ 30/day exists in the model, stays off Admin ├─ Moderation: the only place with actions (#71) ├─ Server: read-only tables ├─ catalog, system, providers, identify history, issue reports

Entitlement design

Do not scatter if (user.isPremium). Keep three separate concepts: FeatureGate (is the product feature released?), Entitlement (is this tier allowed?), and UsageLimit (how much can this account use today?). Premium can exist behind the scenes while pricing/activation stays off.

Admin direction

Admin is an operator console. Decided in #71: Moderation owns every action (edit, scans, hide, delete) with the confirm and the impact counts. Server stays the comfortable read-only table and can link a row into Moderation. Moderation should use that same table layout.
